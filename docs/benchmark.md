# Бенчмаркинг CPU-инференса

## Цель

Оценить задержку и скорость генерации CPU-сервера vLLM для короткого и длинного входного контекста.

Измерения выполняются через Go API Gateway с использованием OpenAI-совместимого streaming API. Таким образом, в результаты входит не только работа vLLM, но и передача ответа через Gateway.

## Окружение

| Параметр | Значение |
| --- | --- |
| Inference engine | vLLM 0.32.0 CPU |
| Модель | Qwen2.5-1.5B-Instruct |
| Развёртывание | Kubernetes / Minikube |
| Конфигурация CPU Minikube | 12 vCPU |
| Лимит памяти Minikube | 14 GiB |
| Максимальная длина контекста | 2048 токенов |
| Интерфейс измерений | Go Gateway, порт 8080 |
| Протокол | HTTP + SSE |
| Параллелизм | Один запрос за раз |

## Методика

Используется скрипт `scripts/benchmark.py` на стандартной библиотеке Python.

Для каждого сценария:

1. Формируется входной промпт заданной длины.
2. Выполняется один прогревочный запрос, который не входит в статистику.
3. Выполняются пять последовательных измерений.
4. Включается потоковый ответ (`stream: true`).
5. Число выходных токенов ограничено `max_tokens: 64`.
6. Для каждого запроса измеряется TTFT и общая длительность.
7. Количество токенов берётся из `usage`, возвращаемого сервером.
8. В качестве итогового значения используется медиана пяти запусков.

Тесты выполняются последовательно, без конкурентных запросов.

Для запуска:

```bash
python3 -u scripts/benchmark.py
```

Исходные данные сохраняются в [benchmark-results.json](benchmark-results.json).

## Метрики

**TTFT (Time to First Token)** — время между началом клиентского HTTP-запроса и получением первого непустого `delta.content` в SSE-потоке.

Это не обычный HTTP TTFB: поток может начаться с события, не содержащего текста.

**Latency** — время между началом HTTP-запроса и завершением SSE-потока.

**Prompt tokens** — число входных токенов, указанное сервером.

**Completion tokens** — число сгенерированных токенов, указанное сервером.

**Decode throughput** — оценка скорости генерации после первого токена:

```text
(completion_tokens - 1) / (latency - TTFT)
```

Первый токен исключён из числителя, поскольку время до него уже учтено в TTFT.

## Анализ

### Влияние длины входного контекста на TTFT

Длина входного контекста увеличилась с 40 до 1828 токенов — приблизительно в 45,7 раза.

При этом медианный TTFT увеличился с 169,4 до 189,8 мс, то есть приблизительно на 12 %.

Таким образом, в измеренном прогретом сценарии увеличение входного контекста сопровождалось относительно небольшим ростом времени до первого содержательного токена.

Этот результат нельзя напрямую интерпретировать как стоимость обработки нового длинного промпта без кэша: в каждом сценарии использовались повторные запросы с одинаковым содержимым.

### Скорость декодирования

Медианная скорость после первого токена составила:

- 11,38 ток/с для короткого промпта;
- 11,23 ток/с для длинного промпта.

Разница составляет примерно 1,3 %.

В данном сценарии длина входного промпта не привела к существенному изменению скорости генерации последующих токенов.

### Полная задержка

Медианная длительность выросла с 4,2976 до 5,8044 с.

Важно, что короткий сценарий завершался после 48 выходных токенов, а длинный генерировал 64 токена. Поэтому разница полной задержки объясняется не только длиной входного контекста, но и разным объёмом генерации.

### Стабильность измерений

Разброс значений TTFT и скорости декодирования между пятью запусками невелик.

Результаты позволяют оценить производительность прогретого CPU inference engine при последовательной нагрузке без конкуренции запросов.

## Ограничения измерений

### Повторяющиеся промпты

Внутри каждого сценария использовался одинаковый промпт. vLLM может повторно использовать промежуточные результаты обработки общего префикса, если соответствующий механизм кэширования включён.

Поэтому показатели TTFT относятся к повторяющейся нагрузке и не характеризуют отдельно холодную обработку каждого нового входного контекста.

### Разное число выходных токенов

Короткий запрос завершился после 48 токенов, а длинный достиг ограничения 64 токена.

Общую задержку этих запросов нельзя использовать как изолированную оценку стоимости prefill.

### Локальное окружение

Измерения проведены на одном локальном Minikube-кластере с CPU backend.

Результаты зависят от доступных ресурсов, фоновой нагрузки, параметров модели, числа потоков и ограничений контейнера.

### Последовательная нагрузка

Запросы выполнялись по одному. Тест не измеряет максимальную пропускную способность системы при нескольких одновременных пользователях.

## Вывод

В проверенном окружении CPU vLLM 0.32.0 обеспечивает потоковую генерацию Qwen2.5-1.5B-Instruct через Go Gateway со скоростью около **11 токенов в секунду**.

Для повторяющихся запросов медианный TTFT составил **169–190 мс** при длине входного контекста от 40 до 1828 токенов.

Полученные показатели описывают производительность прогретой системы при последовательной нагрузке и позволяют сопоставить задержку и скорость генерации для двух размеров промпта.

## Рекомендации по оптимизации throughput

Ниже приведены гипотезы для дальнейшего нагрузочного тестирования,
а не экспериментально подтверждённые улучшения.

### А. Большой поток коротких запросов

Стоит проверить увеличение `max_num_seqs`, чтобы планировщик vLLM
мог одновременно обслуживать больше запросов. Также следует подобрать
`max_num_batched_tokens` для эффективной пакетной обработки.

На CPU увеличение размера пакета ограничено доступными вычислительными
ресурсами и памятью. Поэтому необходимо сравнивать суммарный throughput,
TTFT и задержку при разных уровнях параллелизма.

### Б. Меньше запросов с большим контекстом

Для длинного prefill стоит проверить chunked prefill и настройку
`max_num_batched_tokens`, чтобы управлять обработкой входных токенов
частями и совместной работой prefill и decode.

При необходимости принимать запросы длиннее 2048 токенов потребуется
увеличить `max_model_len`, учитывая расход памяти на KV-кэш.
Само по себе увеличение лимита контекста не ускоряет инференс.

Если длинные запросы имеют общий повторяющийся префикс, стоит
проверить prefix caching: он позволяет переиспользовать
вычисления для совпадающих префиксов.

Оптимальные параметры нужно выбирать на основании сравнительных
замеров на той же CPU-конфигурации.
